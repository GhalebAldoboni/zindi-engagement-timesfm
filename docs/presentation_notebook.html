Predicting New-User Engagement on Zindi¶

Do time-series foundation models (TimesFM-3) help? A pre-registered proof of concept¶

Repository: zindi-engagement-timesfm · Data: Zindi New User Engagement Prediction Challenge (not redistributed)

Contents: 1 Problem · 2 Data loading, X and y · 3 Preparation · 4 Exploratory analysis (Seaborn) · 5 Cross-validation, metric, model and hyper-parameters · 6 Results · 7 Impact and conclusion

1. The problem and why it matters¶

Zindi is Africa's largest data-science competition platform. Like most platforms, it loses most new users quickly: only 11–20% of people who sign up in a month are active the next month.

Task: for each new user, predict from their first (signup) month whether they will be active in the following month (binary classification).

Why it matters. Acquiring a user is far more expensive than keeping one. If the platform knows which new users are likely to return (and which are about to drop), it can:

  • target onboarding help, reminders or competition recommendations at the users most worth contacting, instead of emailing everyone (lower cost, less spam);
  • learn what behaviour in the first month predicts retention, which in turn informs product design.

Research question of this project. Time-series foundation models (Google's TimesFM-3, 2026) produce general-purpose representations of time series. Do embeddings of each user's first-month activity curves add predictive signal beyond carefully engineered features? (Hypotheses H1–H3 were pre-registered.)

3. Preparing the dataset (each step motivated)¶

Step What we did Why
Month order Ordered the masked month codes as 11, 12, 1, …, 5 Tested all 5,040 orders: only this one leaves ~0% of events before signup (0.071%)
Clock alignment Shifted UserActivity by −2 h, then −1 h after a detected switch Its clock ran ahead of the other tables; after the fix 99.94% of "Signed Up" events coincide with signup
Real month lengths 30/31/30/31/31/30 days instead of a 31-day grid Recency and "last 7 days" features must use the true month end
Target y = 1 if the user has any activity next month, excluding badge events A one-day system batch awarded a badge to 2,892 users; counting it made 77% of one cohort "active" (true rate 27%)
Feature window Only signup-month events; nothing from the target month Prevents leakage: the model sees exactly what is known at prediction time
Duplicates Dropped "Joined Competition" activity rows 98.75% duplicate a row of the participation table
Missing values Countries_ID missing for 3,507 users → its own category "missing" Missingness is informative (untracked/incomplete profiles); dropping would lose 28% of users
Categorical encoding Country/FeatureX/FeatureY kept as categories (CatBoost native, levels from training data only) 123 countries: one-hot would be sparse; native handling avoids leakage of unseen levels
Feature generation Per behaviour group (browse, learn, compete, contribute, account, onboarding, badges, comments): count, active days, recency, span, last-7-day count, rate; plus sessions, activity trend, last-active position, competition liveness Engagement theory: how recently, how regularly and in what context a user acts predicts return (motivated by EDA below)
Skewed counts log1p for linear models only Counts are heavy-tailed (browse_count up to 469, mean 6.8); trees do not need it

5. Cross-validation, metric, model and hyper-parameters¶

Validation (motivated by the cohort drift above): rolling-origin folds by signup month.

Fold Train cohorts Validation (tuning, early stopping, threshold) Test
1 0, 1 2 3
2 0, 1, 2 3 4

No random K-fold: users from the future would leak into training. Every fitted object (scalers, PCA, category levels, thresholds) sees training data only; tests/test_no_leakage.py enforces this.

Metric. Classes are imbalanced (11–20% positives), so accuracy is meaningless (predicting "nobody returns" scores 85%). We report F1 (the competition metric; threshold tuned on validation), plus PR-AUC and ROC-AUC (threshold-free; robust to the drift in base rate). Differences between models are tested with a paired bootstrap (2,000 resamples) and reported with 95% confidence intervals.

Models. Baselines: last-7-days rule, logistic regression, random forest, LightGBM (tuned: 30-trial random search on validation PR-AUC, frozen afterwards), MiniRocket. Proposed: TimesFM-3 embeddings (alone and as PCA features in LightGBM). Final: CatBoost on all engineered features (handles categorical variables natively and was best on validation), mean of 5 seeds.

Hypotheses (pre-registered). H1 (embeddings alone underperform): mixed — raw-count embeddings match the GBM, smoothed-curve embeddings are significantly worse. H2 (smoothing helps): reversed. H3 (TimesFM hybrid beats LightGBM): inconclusive — all three confidence intervals include 0.

Why TimesFM did not help. It normalises every series by its own mean and spread, so a series and the same series ×100 get identical embeddings (cosine 1.000): it discards how much a user did, the strongest signal. A custom multi-view network that may weight its inputs per user put only 5% weight on the TimesFM view.

What did help: domain features + CatBoost: +0.036 F1, +0.018 ROC-AUC, +0.033 PR-AUC over tuned LightGBM, all CIs above zero. About 15 very different methods (kernels, XGBoost, stacking, GRU, TabICLv2 2026 tabular foundation model, custom networks) all plateau at the same validation PR-AUC (0.53–0.56): the limit is the information in a new user's first month.

Context. The competition leaderboard's top private scores (0.85–0.87) are not F1 — a confirmed duplicate-ID scoring bug and accuracy-based re-scoring; "predict nobody returns" already gives 0.853 accuracy. Honest entries reached 0.42–0.51 F1; ours (0.48) sits in that band (results/leaderboard_analysis.md).

Does the model solve the problem? Partly — and the analysis shows why "partly" is the ceiling:

  • It ranks new users well (ROC-AUC 0.81; the top 10% return at 3.9× the base rate), which is exactly what a retention team needs to prioritise limited outreach (≈ 80 additional reached future-active users per 200 contacts).
  • It cannot classify every user with certainty (F1 ≈ 0.48–0.50): half of the users who return looked, in their first month, exactly like users who leave. That information is not in the data — no model we tried recovered it.

Applicability. Retrain monthly on the latest cohorts (more recent data helped), use the model as a ranking for targeted engagement, adjust the threshold for the drifting base rate (we tested a drift-aware rule), and monitor the never-tracked segment separately.

Conclusion. For short, sparse engagement logs, a time-series foundation model adds no practical value over engineered features, because its normalisation discards activity level. Understanding the domain (competition liveness, join timing, recency) and an honest time-based evaluation delivered the real, statistically supported improvement.
